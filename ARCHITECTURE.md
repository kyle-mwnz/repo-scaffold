# Architecture

This document describes the architecture of the repository scaffolding system.

## Design Principles

1. **Generate, don't maintain** - Azure Functions code is generated by official tools (`func init`)
2. **Convention over configuration** - Resource names derived from project name
3. **Minimal inputs** - Only 2 user inputs required (project name and API type)
4. **Self-contained** - Each generated project includes all infrastructure code inline
5. **Enable updates** - Projects can pull template updates via `copier update`

## Components

### Repository Scaffolds (`repo-scaffolds`)

**Purpose:** Copier template for creating new project repositories.

**Technology:** [Copier](https://copier.readthedocs.io/) - Python-based project templating with Jinja2.

**Why Copier?**

| Requirement | How Copier Addresses It |
|-------------|-------------------------|
| Variable substitution | Jinja2 templating with rich validation |
| External tools (`func init`) | Task system executes shell commands |
| Template updates | `copier update` pulls changes to existing projects |
| Multiple template types | Conditional logic in single `copier.yml` |
| Cross-platform | Python-based, works on Windows/macOS/Linux |

**Template Structure:**

```
repo-scaffolds/
├── copier.yml                           # Template configuration (2 inputs only)
├── README.md
├── ARCHITECTURE.md
├── docs/
│   ├── copier-template.md
│   ├── developer-guide.md
│   └── naming-conventions.md
└── project/
    └── {{ project_name }}/              # Templated project folder
        ├── .gitignore
        ├── README.md.jinja
        ├── azure-pipelines.yml.jinja    # Standalone build pipeline
        ├── infra/
        │   ├── main.bicep.jinja         # Hello world Bicep
        │   └── parameters/
        │       ├── nonprod.bicepparam.jinja
        │       └── prod.bicepparam.jinja
        ├── src/
        │   └── .gitkeep
        └── tests/
            └── .gitkeep
```

### User Inputs

The template requires only **2 user inputs**:

| Input | Type | Description |
|-------|------|-------------|
| `project_name` | string | Lowercase, alphanumeric with hyphens (3-21 chars) |
| `api_type` | choice | REST API, SOAP API, or Event-driven |

### Computed Variables

| Variable | Value | Purpose |
|----------|-------|---------|
| `dotnet_version` | `"10.0"` | Hardcoded .NET version |
| `pascal_case_name` | Derived from `project_name` | Used for .NET project naming |

### Scaffolded Projects

**Purpose:** Individual service repositories created from the template.

**What's Generated:**

| Component | Technology | Generated By |
|-----------|------------|--------------|
| Azure Functions (.NET 10 isolated) | C# | `func init` + `func new` |
| Unit tests | xUnit | `dotnet new xunit` |
| Infrastructure | Bicep (inline) | Copier template |
| CI/CD Pipeline | Azure Pipelines (build only) | Copier template |

**What's Inline (Self-contained):**

| Component | Description |
|-----------|-------------|
| Pipeline | Standalone build pipeline (no template references) |
| Infrastructure | Hello world Bicep with Storage Account, App Service Plan, Function App |

## Update Mechanisms

### Template Updates (Copier)

When `repo-scaffolds` is updated, existing projects can pull changes:

```bash
cd existing-project
copier update
```

Copier:
1. Reads `.copier-answers.yml` to get original answers and template version
2. Downloads latest template
3. Calculates diff between old and new template output
4. Applies changes, prompting for conflicts

## Environments

Each scaffolded project supports two environments:

| Environment | Purpose | Resource Group Pattern |
|-------------|---------|------------------------|
| `nonprod` | Development and testing | `rg-{project}-nonprod-aue` |
| `prod` | Production workloads | `rg-{project}-prod-aue` |

## Technology Decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Templating tool | Copier | Update mechanism, Jinja2, Python ecosystem |
| Function generation | Azure Functions Core Tools | Official tooling, always current |
| .NET version | 10.0 (hardcoded) | Simplicity, latest LTS |
| Pipeline approach | Standalone build | Simplicity for hello world |
| Infrastructure | Inline Bicep | Self-contained, no external dependencies |
| User inputs | 2 only | Simplicity (project_name, api_type) |
| Naming convention | Derived from project name | Consistency, no manual input errors |
| Environments | NonProd/Prod | Simplicity, covers most use cases |
| Region | Australia East | Current organisational standard |
