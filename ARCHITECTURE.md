# Architecture

This document describes the architecture of the repository scaffolding system.

## Design Principles

1. **Centralise shared components** - Pipeline logic and infrastructure modules are maintained once
2. **Prevent drift** - Projects reference central templates rather than copying them
3. **Enable updates** - Projects can pull template updates via `copier update`
4. **Generate, don't maintain** - Azure Functions code is generated by official tools (`func init`)
5. **Convention over configuration** - Resource names derived from project name

## Components

### 1. Repository Scaffolds (`repo-scaffolds`)

**Purpose:** Copier template for creating new project repositories.

**Technology:** [Copier](https://copier.readthedocs.io/) - Python-based project templating with Jinja2.

**Why Copier?**

| Requirement | How Copier Addresses It |
|-------------|-------------------------|
| Variable substitution | Jinja2 templating with rich validation |
| External tools (`func init`) | Task system executes shell commands |
| Template updates | `copier update` pulls changes to existing projects |
| Multiple template types | Conditional logic in single `copier.yml` |
| Cross-platform | Python-based, works on Windows/macOS/Linux |

**Repository Structure:**

```
repo-scaffolds/
├── copier.yml                           # Template configuration
├── {{ serviceapplication_name }}/                  # Templated project folder
│   ├── azure-pipelines.yml.jinja        # Pipeline config
│   ├── .gitignore
│   ├── README.md.jinja
│   ├── infra/
│   │   ├── main.bicep.jinja
│   │   └── parameters/
│   │       ├── nonprod.bicepparam.jinja
│   │       └── prod.bicepparam.jinja
│   └── src/
│       └── .gitkeep
├── scripts/
│   └── post-scaffold.sh
└── docs/
```

### 2. Pipeline Templates (`pipeline-templates`)

**Purpose:** Centrally-managed Azure Pipeline YAML templates.

**Technology:** Azure Pipelines YAML with template references.

**How It Prevents Drift:**

Projects use the `extends:` keyword to reference templates at runtime:

```yaml
# In scaffolded project's azure-pipelines.yml
resources:
  repositories:
    - repository: templates
      type: git
      name: YourProject/pipeline-templates

extends:
  template: pipelines/function-app-rest.yml@templates
  parameters:
    projectName: $(projectName)
```

When `pipeline-templates` is updated, all projects automatically use the new version on their next pipeline run.

**Repository Structure:**

```
pipeline-templates/
├── templates/
│   ├── stages/
│   │   ├── build-dotnet.yml          # Build .NET projects
│   │   ├── deploy-function.yml       # Deploy Azure Function
│   │   └── deploy-infra.yml          # Deploy Bicep infrastructure
│   ├── jobs/
│   │   ├── dotnet-build.yml
│   │   ├── dotnet-test.yml
│   │   └── bicep-validate.yml
│   └── steps/
│       ├── azure-login.yml
│       └── deploy-bicep.yml
├── pipelines/
│   ├── function-app-rest.yml         # Full pipeline for REST API
│   ├── function-app-soap.yml         # Full pipeline for SOAP API
│   └── function-app-event.yml        # Full pipeline for Event-driven
└── README.md
```

### 3. Bicep Module Registry (`bicep-registry`)

**Purpose:** Centrally-managed Bicep modules for Azure infrastructure.

**Technology:** Azure Container Registry (ACR) with Bicep module support.

**How It Prevents Drift:**

Projects reference modules using the `br:` (Bicep Registry) syntax:

```bicep
// In scaffolded project's main.bicep
module functionApp 'br:youracr.azurecr.io/bicep/function-app:latest' = {
  name: 'functionApp'
  params: {
    name: 'func-${projectName}-${environment}-aue'
    // ...
  }
}
```

Modules are versioned. Projects can:
- Pin to a specific version: `br:acr/bicep/function-app:1.2.0`
- Use latest: `br:acr/bicep/function-app:latest`

**Repository Structure:**

```
bicep-registry/
├── modules/
│   ├── function-app/
│   │   ├── main.bicep
│   │   └── README.md
│   ├── app-insights/
│   │   └── main.bicep
│   ├── storage-account/
│   │   └── main.bicep
│   ├── service-bus/
│   │   └── main.bicep
│   └── apim-api/
│       └── main.bicep
├── compositions/
│   ├── rest-api-stack.bicep
│   ├── soap-api-stack.bicep
│   └── event-driven-stack.bicep
└── azure-pipelines.yml               # Publishes modules to ACR
```

### 4. Scaffolded Projects

**Purpose:** Individual service repositories created from the template.

**What's Centrally Managed (Cannot Drift):**

| Component | Reference Mechanism |
|-----------|---------------------|
| Pipeline build/deploy logic | `extends: template@pipeline-templates` |
| Infrastructure modules | `br:acr/bicep/module:version` |
| .NET SDK version | Defined in central pipeline template |

**What's Project-Owned (Can Evolve):**

| Component | Reason |
|-----------|--------|
| Application code (Functions) | Business logic is unique per project |
| Project-specific config | Environment variables, app settings |
| Documentation | Project-specific README, docs |

## Update Mechanisms

### Template Updates (Copier)

When `repo-scaffolds` is updated, existing projects can pull changes:

```bash
cd existing-project
copier update
```

Copier:
1. Reads `.copier-answers.yml` to get original answers and template version
2. Downloads latest template
3. Calculates diff between old and new template output
4. Applies changes, prompting for conflicts

### Pipeline Updates (Automatic)

No action required. Pipeline templates are fetched at runtime:

```yaml
extends:
  template: pipelines/function-app-rest.yml@templates
```

When `pipeline-templates` main branch is updated, all projects automatically use the new version.

### Bicep Module Updates

Projects using `latest` tag get updates automatically:

```bicep
module functionApp 'br:acr/bicep/function-app:latest' = { ... }
```

For controlled updates, pin to specific versions:

```bicep
module functionApp 'br:acr/bicep/function-app:1.2.0' = { ... }
```

## Environments

Each scaffolded project supports two environments:

| Environment | Purpose | Resource Group Pattern |
|-------------|---------|------------------------|
| `nonprod` | Development and testing | `rg-{project}-nonprod-aue` |
| `prod` | Production workloads | `rg-{project}-prod-aue` |

The pipeline deploys to `nonprod` first, with `prod` requiring approval.

## Security Considerations

### Service Connections

- Azure service connections are referenced by name in pipelines
- Connection names are standardised across the organisation
- Permissions are managed at the Azure DevOps project level

### Secrets Management

- Scaffolded projects include Azure Key Vault integration
- Application settings reference Key Vault secrets
- No secrets are stored in source control

### Pipeline Permissions

- Central templates define which resources pipelines can access
- Individual projects cannot escalate permissions beyond what templates allow

## Extensibility

### Adding a New Template Type

1. Add conditional logic to `copier.yml`:
   ```yaml
   api_type:
     choices:
       REST API: rest
       SOAP API: soap
       Event-driven: event
       New Type: newtype    # Add new choice
   ```

2. Create pipeline template in `pipeline-templates`:
   ```
   pipelines/function-app-newtype.yml
   ```

3. Add conditional Bicep in `main.bicep.jinja`:
   ```jinja2
   {% if api_type == 'newtype' %}
   // New type specific resources
   {% endif %}
   ```

### Adding a New Bicep Module

1. Create module in `bicep-registry/modules/new-module/main.bicep`
2. Publish to ACR via the registry's pipeline
3. Reference in templates: `br:acr/bicep/new-module:1.0`

## Technology Decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Templating tool | Copier | Update mechanism, Jinja2, Python ecosystem |
| Function generation | Azure Functions Core Tools | Official tooling, always current |
| Pipeline approach | `extends:` templates | Prevents drift, centralised control |
| Infrastructure modules | Bicep Registry (ACR) | Versioning, prevents drift, native Azure |
| Naming convention | Derived from project name | Consistency, no manual input errors |
| Environments | NonProd/Prod | Simplicity, covers most use cases |
| Region | Australia East | Current organisational standard |
